## テーブルと共通ルール

CloudFormationの論理IDは `GatchaTable` です。`TableName` は指定せず、CloudFormationが生成する物理名を使用します。実際の名前はスタック出力 `GatchaTableName`、Lambdaからの参照は環境変数 `GATCHA_TABLE_NAME` で確認できます。

| 項目                       | 定義                                                    |
| -------------------------- | ------------------------------------------------------- |
| パーティションキー         | `PK`：文字列（`S`）                                     |
| ソートキー                 | `SK`：文字列（`S`）                                     |
| 課金                       | オンデマンド（`PAY_PER_REQUEST`）                       |
| 暗号化・復旧               | サーバーサイド暗号化、PITR有効                          |
| インデックス               | GSI・LSIなし                                            |
| TTL                        | 未設定。期限の数値属性もTTL属性としては登録していない   |
| スタック削除・テーブル置換 | `DeletionPolicy`、`UpdateReplacePolicy` ともに `Retain` |

複数種類のアイテムを1つのテーブルに格納し、キーの接頭辞で識別します。`entityType` 属性はありません。登録元と作品はBot全体で共用し、投稿設定と履歴は配信先サーバーごとに分けます。

本書のJSON例はDynamoDBの `{"S": "..."}` 形式ではなく、通常のJSONで表します。項目表の型はDynamoDBの `S`（文字列）、`N`（数値）、`BOOL`（真偽値）、`L`（リスト）、`M`（マップ）です。

- Discordのサーバー・チャンネル・メッセージ・Interaction IDは文字列で扱います。
- `leaseUntil`、`until`、`nextAt` はUNIX時刻の秒、`timestamp_ms` はミリ秒です。
- 管理対象の `revision` は、操作したInteraction IDを20桁にゼロ埋めした文字列です。`put_revision` は既存値がない場合、または既存値が新しい値以下の場合だけアイテム全体を置き換えます。同じ操作の再実行を許容し、遅れて届いた古い操作による上書きを防ぎます。
- ジョブ状態の更新は属性単位の `SET` です。明示的に置き換えない属性は残るため、`status` だけから任意属性の有無を断定しないでください。

以下では、登録元サーバーを `222222222222222222`、配信先サーバーを `222222222222222223` とする架空のIDを使用します。

## キー構成の一覧

| データ           | `PK`                        | `SK`                                    | 管理単位                   |
| ---------------- | --------------------------- | --------------------------------------- | -------------------------- |
| 登録元チャンネル | `SOURCES`                   | `CHANNEL#<channel-id>`                  | 登録元チャンネルごと       |
| 登録作品         | `WORKS`                     | `MESSAGE#<message-id>`                  | 元投稿ごと。手動・自動共用 |
| 自動投稿設定     | `TIMERS`                    | `GUILD#<guild-id>`                      | 配信先サーバーごとに1件    |
| 投稿履歴         | `HISTORY#<mode>#<guild-id>` | `<timestamp_msの16桁ゼロ埋め>#<job-id>` | 配信先・手動／自動ごと     |
| ジョブ状態       | `JOB#<job-id>`              | `STATE`                                 | 管理・手動・自動の各ジョブ |
| 配信ロック       | `LOCK#<mode>#<guild-id>`    | `STATE`                                 | 配信先・手動／自動ごと     |
| クールダウン     | `COOLDOWN#<guild-id>`       | `MANUAL`                                | 配信先サーバーごと         |

`mode` は大文字の `MANUAL` または `AUTO` です。ソース系のキーにはサーバーIDを含めません。単一の `GatchaSourceGuildId` を登録元とする構成です。

## 登録元チャンネル

`/gatcha channel add/remove` が書き込みます。通常のテキスト／アナウンスチャンネルを登録し、スレッドは対象外です。

| 属性         | 型    | 意味                                                  |
| ------------ | ----- | ----------------------------------------------------- |
| `PK` / `SK`  | S / S | `SOURCES` / `CHANNEL#<channel-id>`                    |
| `channel_id` | S     | 登録元チャンネルID                                    |
| `active`     | BOOL  | `true` ならこのチャンネルの有効作品を抽選候補にできる |
| `revision`   | S     | 最後に適用した管理操作の世代                          |

```json
{
  "PK": "SOURCES",
  "SK": "CHANNEL#333333333333333333",
  "channel_id": "333333333333333333",
  "active": true,
  "revision": "00777777777777777777"
}
```

`channel remove` はこのアイテムを `active: false` にします。`WORKS` の各アイテムは削除・更新しません。再追加すると、個別に解除・無効化されていない作品が再び抽選候補になります。

## 登録作品

メッセージのアプリメニュー `gatcha register/remove` が書き込みます。元投稿の参照情報だけを保持し、配信時にDiscordから最新の本文・添付・投稿者情報を取得します。

| 属性         | 型    | 意味                                                                       |
| ------------ | ----- | -------------------------------------------------------------------------- |
| `PK` / `SK`  | S / S | `WORKS` / `MESSAGE#<message-id>`                                           |
| `message_id` | S     | 元投稿のメッセージID                                                       |
| `channel_id` | S     | 元投稿のチャンネルID                                                       |
| `active`     | BOOL  | 個別の抽選対象フラグ                                                       |
| `source_url` | S     | `https://discord.com/channels/<source-guild-id>/<channel-id>/<message-id>` |
| `revision`   | S     | 最後に適用した登録・解除操作の世代                                         |

```json
{
  "PK": "WORKS",
  "SK": "MESSAGE#444444444444444444",
  "message_id": "444444444444444444",
  "channel_id": "333333333333333333",
  "active": true,
  "source_url": "https://discord.com/channels/222222222222222222/333333333333333333/444444444444444444",
  "revision": "00777777777777777777"
}
```

抽選には作品自身と登録元チャンネルの両方の `active` が必要です。個別解除は情報を残して `active: false` にし、未登録の投稿を解除した場合も無効なアイテムを作ります。これにより、先に受け付けた古い登録操作が後から届いても復活を防げます。

配信時に元投稿が `Unknown Message`（HTTP 404、Discordコード10008）だった場合も `active: false` にします。この自動無効化では `revision` を変更しません。権限不足、空の投稿、容量超過などでその回だけ候補から外した作品は、このフラグを変更しません。

## 自動投稿設定

`/gatcha timer config` が、指定サーバーの設定全体を置き換えます。投稿先と週1枠の曜日・時刻を保持します。

| 属性           | 型           | 意味                                           |
| -------------- | ------------ | ---------------------------------------------- |
| `PK` / `SK`    | S / S        | `TIMERS` / `GUILD#<guild-id>`                  |
| `guild_id`     | S            | 配信先サーバーID                               |
| `channel_id`   | S            | 配信先チャンネルID。有効な設定で保存           |
| `slots`        | L（要素はM） | 投稿枠。有効な設定で保存                       |
| `slots[].day`  | N            | JSTの曜日。月曜=`0`〜日曜=`6`                  |
| `slots[].hour` | N            | JSTの時刻。`0`〜`23`。分は毎正時               |
| `active`       | BOOL         | `true` なら自動投稿を有効にする                |
| `version`      | S            | 設定・停止操作のInteraction ID。ゼロ埋めなし   |
| `revision`     | S            | 同じInteraction IDを20桁にゼロ埋めした管理世代 |

次は毎週月曜09:00（JST）の例です。

```json
{
  "PK": "TIMERS",
  "SK": "GUILD#222222222222222223",
  "guild_id": "222222222222222223",
  "channel_id": "333333333333333334",
  "slots": [{"day": 0, "hour": 9}],
  "active": true,
  "version": "777777777777777777",
  "revision": "00777777777777777777"
}
```

コマンドの曜日・時刻は別々の選択リストですが、保存時は1要素の `slots` 配列に変換します。旧形式の複数枠が保存済みなら、再設定するまでスケジューラはそれらも処理します。旧データでは `active` がない場合も有効として読みます。

`/gatcha timer remove` はアイテムを物理削除せず、停止を表す次の形に置き換えます。`channel_id` と `slots` は保持しません。

```json
{
  "PK": "TIMERS",
  "SK": "GUILD#222222222222222223",
  "guild_id": "222222222222222223",
  "active": false,
  "version": "777777777777777778",
  "revision": "00777777777777777778"
}
```

自動投稿のSQSジョブは生成時の `version` を `timer_version` として持ちます。ワーカーは現在の設定が有効で、世代とチャンネルが一致することを配信準備前と送信前に確認します。変更・停止前のジョブは `SKIPPED` にし、古い設定による投稿を防ぎます。

## 投稿履歴

配信成功を記録するアイテムです。手動／自動、配信先サーバーごとに分け、履歴を抽選の重複除外に使います。

| 属性                | 型  | 意味                                                                       |
| ------------------- | --- | -------------------------------------------------------------------------- |
| `PK`                | S   | `HISTORY#MANUAL#<guild-id>` または `HISTORY#AUTO#<guild-id>`               |
| `SK`                | S   | `timestamp_ms` の16桁ゼロ埋めと `job-id` を `#` で連結                     |
| `guild_id`          | S   | 配信先サーバーID                                                           |
| `channel_id`        | S   | 配信先チャンネルID                                                         |
| `mode`              | S   | `MANUAL` または `AUTO`                                                     |
| `message_id`        | S   | 抽選した元投稿のメッセージID                                               |
| `source_url`        | S   | 元投稿のURL                                                                |
| `timestamp_ms`      | N   | 送信直前に記録したUNIX時刻（ミリ秒）。履歴の並び順に使用                   |
| `posted_at`         | S   | 同じ送信直前の時点を表すUTCのISO 8601文字列。Discordが返す投稿時刻ではない |
| `posted_message_id` | S   | 送信成功応答から取得した配信先のメッセージID                               |

```json
{
  "PK": "HISTORY#MANUAL#222222222222222223",
  "SK": "0001767225600000#777777777777777777",
  "guild_id": "222222222222222223",
  "channel_id": "333333333333333334",
  "mode": "MANUAL",
  "message_id": "444444444444444444",
  "source_url": "https://discord.com/channels/222222222222222222/333333333333333333/444444444444444444",
  "timestamp_ms": 1767225600000,
  "posted_at": "2026-01-01T00:00:00+00:00",
  "posted_message_id": "666666666666666666"
}
```

同じパーティションを `ScanIndexForward=False`、`Limit=10` でQueryし、直近10件を取得します。配信先チャンネルが変わってもサーバーと実行種別が同じなら履歴を引き継ぎます。有効作品が10件以下なら履歴による除外を行わず、11件以上ならその10件の元投稿IDを除外します。

履歴のPutとジョブの `SUCCESS` 更新は、同じ `TransactWriteItems` で確定します。`DELIVERED` から履歴確定を再試行するときは、ジョブに保存済みの `history` を使うため履歴キーも変わりません。履歴は10件だけに切り詰めず、成功した配信分を保持します。

## ジョブ状態

SQSによる重複受信と再試行に対応するための状態です。管理操作にも作成し、SQSの本文全体は保存しません。

| 属性         | 型           | 意味・保存条件                                                                                       |
| ------------ | ------------ | ---------------------------------------------------------------------------------------------------- |
| `PK` / `SK`  | S / S        | `JOB#<job-id>` / `STATE`                                                                             |
| `status`     | S            | 以下の処理状態                                                                                       |
| `leaseUntil` | N            | `claim` した時刻から80秒後のUNIX時刻。期限超過で最初から処理しないジョブなどには存在しない場合がある |
| `skipped`    | L（要素はS） | そのジョブで候補から外した元投稿IDの保存済みリスト。再試行時に引き継ぐ。必要な場合に追加             |
| `history`    | M            | 送信直前に作る履歴情報。履歴アイテムの業務属性と同じで、`PK` / `SK` は含まない                       |
| `result`     | S            | 終了理由などの識別子。設定する経路だけで保存され、常に存在する属性ではない                           |

### ジョブID

| 実行種別           | IDの作り方                                                            |
| ------------------ | --------------------------------------------------------------------- |
| 管理操作・手動抽選 | DiscordのInteraction ID                                               |
| 自動投稿           | `SHA-256("<guild-id>#<予定日時のUNIX秒>")` の先頭24文字（16進文字列） |

同じサーバー・予定日時の自動投稿は、Schedulerから複数回投入されても同じIDになります。設定の世代は自動ジョブIDには含めず、SQSの `timer_version` で照合します。

### 状態と再試行

配信成功時の主な流れは `RUNNING → SENDING → DELIVERED → SUCCESS` です。

| `status`    | 意味                                                     | 再受信時の扱い                                            |
| ----------- | -------------------------------------------------------- | --------------------------------------------------------- |
| `RUNNING`   | 処理権を取得し、管理操作または配信準備を実行中           | リース中は再試行待ち。期限を過ぎた `RUNNING` は再取得可能 |
| `RETRY`     | 一時障害などで再試行待ち                                 | 再取得して処理を再開                                      |
| `SENDING`   | Discordへ送信し得る境界を保存済み                        | リース中は待ち、期限を過ぎたら `UNKNOWN` にする           |
| `DELIVERED` | 送信成功応答と配信先メッセージIDを保存済み               | 再送せず、履歴と `SUCCESS` の確定だけを再開               |
| `SUCCESS`   | 管理操作、または配信と履歴確定が完了                     | 終端状態。追加処理しない                                  |
| `FAILED`    | 候補なし、権限・引数不備、古い管理操作などで失敗         | 終端状態。追加処理しない                                  |
| `UNKNOWN`   | 送信結果が確定できない                                   | 終端状態。重複回避のため自動再送しない                    |
| `EXPIRED`   | ジョブの実行期限を超過                                   | 終端状態。配信しない                                      |
| `SKIPPED`   | 配信先が許可対象外、または自動投稿設定が変更・停止された | 終端状態。配信しない                                      |

管理操作は通常 `RUNNING → SUCCESS` となり、`history` を持ちません。送信時の容量超過が確定した場合は、作品を `skipped` に追加して `SENDING → RUNNING` に戻り、別の作品を選びます。

`history` は `SENDING` の時点では `posted_message_id` を含まず、`DELIVERED` への更新時に追加します。次は送信成功を保存し、履歴確定まで完了した例です。

```json
{
  "PK": "JOB#777777777777777777",
  "SK": "STATE",
  "status": "SUCCESS",
  "leaseUntil": 1767225680,
  "history": {
    "guild_id": "222222222222222223",
    "channel_id": "333333333333333334",
    "mode": "MANUAL",
    "message_id": "444444444444444444",
    "source_url": "https://discord.com/channels/222222222222222222/333333333333333333/444444444444444444",
    "timestamp_ms": 1767225600000,
    "posted_at": "2026-01-01T00:00:00+00:00",
    "posted_message_id": "666666666666666666"
  }
}
```

`result` には、失敗時の `not_delivered`、期限超過時の `deadline_exceeded`、スキップ時の `guild_not_allowed` / `timer_changed`、送信結果不明時の `discord_delivery_unknown` / `worker_interrupted_during_send` / `storage_or_worker_failure_after_send_started` を保存する経路があります。送信直前の期限超過など、`result` を設定せず状態だけを更新する経路もあります。

SQSジョブの `deadline` は自動投稿が予定時刻から300秒、管理操作・手動抽選が受付時刻から840秒です。`deadline` 自体はDynamoDBに保存しません。`DELIVERED` の履歴確定と `SENDING` の確認は、期限判定より先に行います。Discordへの送信とDynamoDB更新を単一トランザクションにはできないため、`UNKNOWN` は実際のDiscord投稿と照合して判断します。

## 配信ロック

同じ配信先サーバー・同じ実行種別の抽選処理を直列化します。管理操作はこのロックを取得しません。

| 属性        | 型    | 意味                               |
| ----------- | ----- | ---------------------------------- |
| `PK` / `SK` | S / S | `LOCK#<mode>#<guild-id>` / `STATE` |
| `owner`     | S     | ロックを取得したジョブID           |
| `until`     | N     | 取得時刻から80秒後のUNIX時刻       |

```json
{
  "PK": "LOCK#MANUAL#222222222222222223",
  "SK": "STATE",
  "owner": "777777777777777777",
  "until": 1767225680
}
```

アイテムがない場合、または `until` が現在時刻より前の場合だけ、条件付きPutで取得します。解放時は `owner` が自分のジョブIDである場合だけ削除します。処理中断で残っても期限後は取得可能ですが、時刻経過だけで物理削除はされません。`MANUAL` と `AUTO` のロックは別なので、手動抽選と自動投稿を互いに排他するものではありません。

## 手動抽選のクールダウン

手動抽選の「サーバーごとに30秒に1回」を管理します。ユーザーやチャンネルによらず共有し、自動投稿には適用しません。

| 属性        | 型    | 意味                             |
| ----------- | ----- | -------------------------------- |
| `PK` / `SK` | S / S | `COOLDOWN#<guild-id>` / `MANUAL` |
| `nextAt`    | N     | 次の別ジョブを受け入れるUNIX時刻 |
| `jobId`     | S     | 最後に受け入れたジョブID         |

```json
{
  "PK": "COOLDOWN#222222222222222223",
  "SK": "MANUAL",
  "nextAt": 1767225630,
  "jobId": "777777777777777777"
}
```

アイテムがない、`nextAt` が現在時刻以下、または同じ `jobId` の再試行である場合に更新できます。更新すると `nextAt` はその処理時刻から30秒後になります。配信ロックの取得後、作品選択前に更新するため、最終的な投稿成功の有無だけで決まる制限ではありません。

## 主なアクセスパターン

| 処理                 | 読み書きするアイテム・操作                                                          |
| -------------------- | ----------------------------------------------------------------------------------- |
| 登録元の追加・解除   | `SOURCES` を管理世代付きPut                                                         |
| 作品の登録・解除     | 対象の `SOURCES` / `WORKS` をGetし、`WORKS` を管理世代付きPut                       |
| 自動投稿の設定・停止 | `TIMERS` を管理世代付きPut                                                          |
| 毎正時の対象判定     | `PK=TIMERS` をQueryし、許可済みサーバー、有効フラグ、JSTの曜日・時刻で判定          |
| 配信の抽選準備       | `SOURCES` / `WORKS` をQueryし、有効作品を選別。対応する `HISTORY` の直近10件をQuery |
| 配信直前の再確認     | 対象 `SOURCES` / `WORKS`、自動投稿なら `TIMERS` をGet                               |
| 重複制御・再試行     | `JOB` をGet・条件付きUpdate。`LOCK` を条件付きPut・Delete                           |
| 手動抽選の頻度制限   | `COOLDOWN` を条件付きUpdate                                                         |
| 配信成功の確定       | 履歴のPutと `JOB.status=SUCCESS` のUpdateをトランザクションで実行                   |

`Store.get` と `Store.query` は強い整合性の読み取り（`ConsistentRead=True`）を使用します。通常のQueryはページングして取得し、履歴の直近件数指定では1回のQuery結果を返します。現行処理はScanやインデックスを使いません。

受付Lambdaはこのテーブルにアクセスせず、SQSへジョブを投入します。配信ワーカーがデータを読み書きし、定時起動Lambdaは `TIMERS` をQueryします。IAMとAWSリソース間の関係は [システム構成](system-architecture.md) を参照してください。

## 保持と保存先の境界

TTLと定期削除処理はありません。登録元・作品の解除は原則として無効化、タイマー停止は停止世代の保存です。配信ロックは通常の解放時に削除しますが、履歴・ジョブ・クールダウンは処理後も残ります。`leaseUntil`、`until`、`nextAt` はアプリケーションの判定時刻であり、DynamoDBによる自動削除の指定ではありません。

| 情報                                                                        | 保存先・扱い                                                                                     |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 元投稿のID・URL、設定、履歴、ジョブ状態                                     | 本書の `GatchaTable`                                                                             |
| 元投稿の本文、添付ファイル本体、CDN URL、投稿者名・アイコン                 | 配信時にDiscord API／CDNから取得し、DynamoDBへ保存しない                                         |
| Interaction Token、コマンド引数、ジョブの受付時刻・期限、アプリケーションID | SQSジョブで引き継ぐ。DynamoDBにはジョブ状態など必要な情報だけを保存                              |
| Bot Token                                                                   | Parameter StoreのSecureString。ワーカーが取得し、テーブルへ保存しない                            |
| DiscordメンバーIDとWebメンバーIDの対応                                      | `aitc-web-infra` 側で管理。BotはIAM認証の逆引きAPIを呼び、テーブルへキャッシュしない             |
| 配信済みの本文・添付                                                        | Discordの配信先メッセージ。履歴にはID・元投稿URL・時刻などのメタデータを保存し、内容を複製しない |

状態を手動で削除・書き換えると、重複送信防止や古い管理操作の拒否に影響します。特に `UNKNOWN` の機械的なリセットや、停止世代の削除は行わず、[gatchaの運用仕様](gatcha.md#実行と保存) と実際の投稿・キューの状態を確認して判断してください。
