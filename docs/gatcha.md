# gatcha コマンドと配信基盤

issue #3 の仕様・運用手順です。`design.md` の `/ping` 初期版に、本書のDynamoDB・SQS・ワーカー・Schedulerを追加します。`/ping` は引き続きネットワークを呼ばず、本人向けに応答します。

## コマンドと権限

| 操作 | 実行場所・権限 | 動作 |
| --- | --- | --- |
| `/gatcha draw [server:aitc]` | 許可済み全サーバーの全メンバー | 実行チャンネルへ作品を公開投稿。サーバー全体で30秒に1回 |
| `/gatcha channel add` | AITC、管理者ロール | 実行したチャンネルを作品の登録元に追加 |
| `/gatcha channel remove` | AITC、管理者ロール | 実行したチャンネルの全作品を抽選対象から外す |
| メッセージのアプリメニュー → `gatcha register` | AITC、管理者ロール | 右クリックした投稿を登録 |
| メッセージのアプリメニュー → `gatcha remove` | AITC、管理者ロール | 右クリックした投稿を抽選対象から外す |
| `/gatcha timer config guild:<ID> channel:<ID> day:月曜 hour:09:00` | AITC、管理者ロール | 指定サーバーの投稿先と週1枠の曜日・時刻を置換 |
| `/gatcha timer remove guild:<ID>` | AITC、管理者ロール | 指定サーバーの自動投稿設定を削除 |

管理者ロールは **`840827308251283456`** の保持をコード側で判定します。DiscordのAdministrator権限だけでは代用しません。管理コマンドは登録元サーバーだけに登録し、他の許可済みサーバーには `draw` を登録します。管理操作の結果は本人だけに表示します。

登録元は通常のテキスト／アナウンスチャンネルです。スレッドは登録できず、親チャンネルからの許可継承もありません。チャンネルを解除しても作品の登録情報を保持し、再追加すると、個別に解除・無効化されていない作品が抽選対象へ戻ります。作品の登録一覧は手動・自動で共用します。

投稿先サーバーは既存の `AllowedGuildIds` で管理します。自動投稿は1サーバー1チャンネル・週1枠です。`day` と `hour` は別々の選択リストで、曜日は月曜〜日曜、時刻は日本時間（JST）の `00:00`〜`23:00` からそれぞれ1つ選びます。分指定や複数選択はできません。上記の例では毎週月曜09:00に投稿します。再実行すると、そのサーバーの投稿先と曜日・時刻をすべて置き換えます。

内部値は曜日が `MON`〜`SUN`、時刻が整数 `0`〜`23` です。保存形式は既存の `slots` 配列を維持し、新しい設定は1要素として保存します。旧形式で保存済みの複数枠は更新するまで継続し、次の `timer config` で週1枠に置き換わります。

## 抽選と表示

- 有効な登録元チャンネルの有効作品が10件以下なら、全作品から抽選します。11件以上なら、同じ配信先サーバー・同じ実行種別の直近10件を除外します。手動の履歴を自動抽選へ混ぜません。
- 配信時に元投稿を取得し、最新の本文と添付を使用します。`Unknown Message`（404、Discordコード10008）の作品は情報を残して無効化し、引き直します。権限不足や一時障害を削除と見なしません。
- 取得できない作品、空の作品、容量制限を超える作品は、その回だけスキップします。候補がなくなった場合は配信せず、手動では実行者へ案内します。
- Components V2のContainer内に、投稿者名・アイコン、本文、画像のMedia Gallery、音声等のFile、プロフィールへのリンクを表示します。画像もファイルも再添付し、元の署名付きCDN URLを長期保存しません。
- 本文や名前から通知を発生させません。スポイラー指定を維持します。Discordの本文・添付・送信容量上限に収まらない作品は分割・切り捨てず、その回の抽選から外します。最大送信要求25 MiBに対し、ダウンロード合計は24 MiBまでとします。
- BotはIAM署名でWeb APIの逆引きルートを呼び、既存の `/members-only/members/profile?id=<member-id>` にリンクします。対応が404ならボタンを省略し、API障害なら配信前の再試行に回します。

## 実行と保存

受付LambdaはDiscordの署名・許可サーバー・管理者ロール・引数を検証してSQSへ投入し、遅延応答を返します。キューは3秒遅延して、Discordが受付応答を保存する前の編集を避けます。本文取得・再添付・公開はワーカーLambdaが担当します。

共通のEventBridge Schedulerが1時間ごと（JSTの毎正時の枠、柔軟な時間枠OFF）に起動します。設定テーブルから該当するサーバーを選び、配信先ごとのジョブをSQSへ投入します。タイマー設定の世代をジョブに含め、待機中に変更・削除された設定による投稿を止めます。

管理操作はInteraction IDを世代として条件付き保存し、古いキュージョブの再処理で新しい設定を上書きしません。`timer remove` は投稿先・投稿枠を消し、停止世代だけを保持します。これにより、遅れて届いた古い設定ジョブからの復活も防ぎます。

DynamoDBでは `SOURCES`、`WORKS`、`TIMERS`、`HISTORY#MANUAL#<guild>`、`HISTORY#AUTO#<guild>`、`JOB#<id>`、サーバー別ロックとクールダウンを分離します。履歴は配信日時（UTC ISOとepochミリ秒）、元投稿URL、元投稿ID、配信先サーバー／チャンネル、配信メッセージIDを記録し、TTLを設けません。テーブル削除をRetainし、暗号化とPITRを有効にします。

Interaction ID、または配信先と予定日時から作るIDで重複ジョブを識別します。同じサーバー・実行種別の抽選をロックで直列化します。送信前に `SENDING` を保存し、成功応答後に `DELIVERED` を保存してから、成功履歴と `SUCCESS` を同じDynamoDBトランザクションで確定します。

- `DELIVERED` の再処理は履歴の確定だけを行い、Discordへ再送しません。
- 通信タイムアウト、送信の5xx、送信途中のワーカー停止は `UNKNOWN` として再送を止めます。未配信の可能性を許容し、重複回避を優先する運用です。
- 自動投稿の期限は予定日時から300秒です。SQS再配信でも元の期限を引き継ぎ、期限後は投稿しません。手動の期限は受付から14分です。
- キュー可視性90秒、ワーカー上限60秒、ジョブとロックのリース80秒です。最大受信回数5回でDLQへ移します。DLQを再投入する場合も、期限と送信状態を確認してください。`UNKNOWN` を機械的にリセットしないでください。

キューはSSEで暗号化します。Interaction Tokenは短命なキュージョブだけに含め、DynamoDBやログには保存しません。Bot TokenはワーカーがParameter StoreのSecureStringから取得し、Lambda環境変数にはパラメーター名だけを設定します。受付・定時起動LambdaにはToken取得権限を与えません。ログはジョブID・結果・例外型に限定し、本文・添付・Token・署名付きURLを出しません。

## 導入・更新

1. `aitc-web-infra` の逆引きAPIを先にデプロイします。メンバーCSVへ任意の `discordId` 列を追加し、既存の変換・インポートで取り込みます。ID未登録のメンバーはそのまま利用できます。
2. Webスタック出力 `DiscordMemberLookupApiId` とリージョンをBot設定の `WebLookupApiId`／`WebLookupRegion` に設定します。同じAWSアカウントのAPI Gatewayへ直接IAM署名して呼びます。`GatchaSourceGuildId` はAITCサーバーIDで、`AllowedGuildIds` に含めます。`WebProfileBaseUrl` は既存WebサイトのHTTPS Originです。
3. Discord Developer Portalで **MESSAGE CONTENT INTENT** を有効化します。Botに登録元の閲覧・メッセージ履歴の閲覧、配信先のメッセージ送信・ファイル添付・埋め込みリンクの権限を付けます。Botが必要な全サーバーに導入されていることを確認します。
4. 既存のBot TokenをSecureStringに保存したうえで `scripts/test.ps1`、`scripts/build.ps1`、`scripts/deploy.ps1` を実行し、変更セットを確認して適用します。AWS SDKも `requirements.txt` の固定版をZIPへ含めます。通常デプロイではDiscordコマンドを変更しません。
5. `scripts/sync-commands.ps1` を明示的に実行してコマンドを登録します。曜日・時刻の選択リストへの更新時も、Lambdaをデプロイした後にこの同期が必要です。`/ping` と同名upsertを使用し、無関係なコマンドを一括削除しません。
6. AITCの作品チャンネルで `channel add` を実行し、投稿のアプリメニューから作品を登録します。手動抽選と、サーバーを指定した `timer config` を確認します。

`design.md` とREADMEの旧Bot切り替えは初期 `/ping` 移行時の手順です。旧移行のRestoreは `/ping` だけを新コマンドとして扱うため、gatcha導入後の復旧には本書の手順を使用します。コードを戻す場合はまず `timer remove` で各自動投稿を停止し、キューの処理状態を確認してから、保持した前バージョンのテンプレートとZIPで変更セットを作成します。コマンドを戻す際は保存した定義を個別にupsertし、新コマンドの削除も明示的に行います。DynamoDBは保持し、旧テンプレートへ戻す変更セットにテーブル・キューの削除が含まれる場合は処理中のジョブを確認してください。

## 受入確認

ローカルテストはAWS・Discordをモックし、外部の投稿や本番設定を変更しません。権限、10/11件の境界、手動／自動の独立、30秒制限、スレッド除外、削除・容量超過、送信結果不明、履歴確定の再開、JSTと設定世代の扱いを確認します。

実環境では、一般メンバーの公開抽選、管理者以外の拒否、画像・音声の再添付、プロフィールの認証付き閲覧、タイマーの置換・停止を確認してください。コールドスタートを含むDiscordの3秒以内の初回応答、定時枠の配信、削除済み投稿の引き直し、CloudWatchの `UNKNOWN` とDLQも確認します。送信とDynamoDBを単一トランザクションにはできないため、`SENDING` のまま止まったジョブは実投稿と照合して判断します。
